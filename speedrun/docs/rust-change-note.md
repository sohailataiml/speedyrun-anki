# The Rust change: mastery query

## What it is

A new read-only backend RPC, `StatsService.MasteryQuery`, that takes a list of
topic names and returns, per topic: mean current FSRS retrievability
("mastery"), the proportion of graded reviews rated above "Again" ("average
recall"), and card coverage counts (`cards_with_reviews` / `cards_total`). A
topic is a `topic::<name>` tag on a note — no new schema, just a tag
namespace.

## Why this belongs in Rust, not Python or per-client code

**It has to run identically and fast on both the desktop and the phone.**
Anki's Rust core (`rslib`) is the one layer both the desktop Qt app and the
Android client (via AnkiDroid's JNI bridge) actually share. Computing mastery
in Python on desktop and separately in Kotlin on Android would let the two
platforms' numbers drift the moment either implementation changed — exactly
the kind of two-client inconsistency the PRD's "two apps, one engine"
non-negotiable is meant to prevent. Writing it once in Rust and exposing it
through the existing protobuf boundary means both clients call the same
code path.

**It needs FSRS internals that only exist in Rust.** Retrievability
(`fsrs::current_retrievability`) is computed from a card's `memory_state`
(stability/difficulty) and decay — types and a function that live in
`rslib`/the `fsrs` crate. Reimplementing that math in Python would mean
re-deriving FSRS's retrievability formula a second time and keeping it in
sync by hand; every other stats feature in this codebase (`card_stats`,
`graphs`) already accesses `memory_state` this way for the same reason.

**It has to be fast at 50k cards.** The implementation does one tag search
per topic (`tag:topic::<name>`, backed by Anki's existing indexed search) and
then exactly two batched queries against that result set —
`all_searched_cards()` and `get_revlog_entries_for_searched_cards()` — via
the same `search_cards_into_table` + temp-table pattern the existing
`graphs` stats query uses. There is no per-card query in the loop, so cost
scales with topics × cards-per-topic, not with a query per card. This
mirrors the one performance-sensitive pattern already established in this
codebase for exactly this kind of aggregate query.

## Undo safety and collection integrity

The query is read-only end to end. It opens a temporary `search_cids` table
(cleaned up automatically when the guard drops — the same mechanism
`graph_data_for_search` uses), fetches cards and revlog entries, and returns
computed values. It never calls `update_card`, `add_revlog_entry`, or
anything that touches the undo log or bumps the collection's mod time in
the non-test code path. There is nothing to undo because nothing is
written. (The `update_card` / `add_revlog_entry` calls visible in
`rslib/src/stats/mastery.rs` are confined to `#[cfg(test)]` — they build
fixture data for the tests, not part of the query itself.) The Rust unit
tests exercise this: `topics_are_isolated_from_each_other` runs the query
twice in a row against the same collection and gets consistent, correct
results both times, which would not be true if the query mutated shared
state.

## What would prove this design wrong

If a real 50,000-card deck with a realistic number of topics (a few hundred)
showed the mastery query taking anywhere near as long as the
per-topic-search cost times the number of topics (i.e., if the batching
weren't actually saving anything), that would mean the `search_cids`
temp-table approach isn't paying for itself at this scale, and a real SQL
aggregate query (computed once across all topics, joined against a
topic-to-card mapping table) would be the honest fix — see `tools/bench/`
for where this should be measured once real Speedrun content exists.

## Upstream files touched

- `proto/anki/stats.proto` — new `MasteryQuery` RPC, `MasteryQueryRequest`,
  `MasteryQueryResponse`, `TopicMastery` messages.
- `rslib/src/stats/mod.rs` — registered the new `mastery` submodule.
- `rslib/src/stats/mastery.rs` — new file: the query implementation and its
  3 Rust unit tests.
- `rslib/src/stats/service.rs` — wired `MasteryQuery` into
  `StatsService for Collection`.
- `pylib/anki/collection.py` — added `Collection.mastery_query()`, a thin
  typed wrapper over the generated backend call (matching the existing
  `card_stats_data` convention).

  Python test).
- `out/pylib/anki/_backend_generated.py` — auto-regenerated by the build
  from the `.proto` change; not hand-edited.

## Shipped to Android

AnkiDroid does not compile Anki's Rust backend from source by default — it
depends on a prebuilt third-party Maven artifact
(`io.github.david-allison:anki-android-backend`). To get this feature onto
the phone: `apps/Anki-Android-Backend` (the JNI bridge project) was cloned
as a sibling of `apps/android` per its own documented local-dev workflow,
its `anki` git submodule was pointed at this fork's commit instead of
upstream, and it was built locally (`cargo run -p build_rust`, cross-
compiling `rsdroid` for `x86_64-linux-android` via `cargo-ndk`) to produce
`rsdroid-release.aar`. `apps/android/local.properties` sets
`local_backend=true`, which makes AnkiDroid's Gradle build link that local
AAR instead of the Maven dependency.

Two small compatibility fixes were needed, both isolated to tooling/AnkiDroid's
own code, not this repo's Rust change:
- `Anki-Android-Backend/build_rust/src/main.rs`: the Gradle wrapper was
  invoked as a bare `gradlew.bat`, which fails on this machine because
  `NoDefaultCurrentDirectoryInExePath=1` is set (a Windows hardening
  setting that disables cmd.exe's implicit current-directory search) —
  changed to the explicit `.\gradlew.bat`.
- `apps/android/libanki/.../Deck.kt`: AnkiDroid's Kotlin code predates a
  newer `Order` enum variant (`RELATIVE_OVERDUENESS`) that exists in this
  fork's more recent anki base, so its exhaustive `when` needed one added
  branch.

Verified: `GeneratedBackend.kt` now exposes
`fun masteryQuery(topics: Iterable<String>): List<anki.stats.TopicMastery>`,
the APK builds and installs, and the app runs on an emulator against a real
collection with no crashes.
